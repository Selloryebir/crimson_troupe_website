# Git 分支职责与同步工作流

## 目的

本文件是仓库长期分支职责、允许的合并方向和人工门禁的唯一完整说明。它用于避免蓝图规划、源码实现、阶段集成和正式发布互相污染；所有人员与智能体在执行 commit、push、创建合并请求或合并前都必须先确认当前分支及本文件约束。

用户当次明确指令仍然优先，但一次授权只覆盖被明确指定的 Git 操作，不自动扩张为后续 push、合并或发布权限。

## 分支职责

| 分支            | 核心职责                             | 允许的主要来源  | 允许的主要去向         |
| --------------- | ------------------------------------ | --------------- | ---------------------- |
| `main`          | 人工审核后的稳定主线                 | 仅 `dev`        | 不作为日常开发同步来源 |
| `dev`           | 可部署、可浏览的阶段里程碑集成       | 仅 `dev_code`   | `main`                 |
| `dev_blueprint` | 蓝图、设计、规划、文档治理与阶段统筹 | `dev_code`      | `dev_code`             |
| `dev_code`      | 依据 active 蓝图实现和迭代源码       | `dev_blueprint` | `dev_blueprint`、`dev` |

“分支职责”限制的是新改动应在哪里产生，不要求分支只包含某类文件。`dev_blueprint` 可以通过正式合并接收 `dev_code` 已实现的源码，从而基于真实实现继续规划；但不得在 `dev_blueprint` 上主动开发 `src/` 功能。

## `main`：人工控制的稳定主线

- `main` 只接受来源为 `dev` 的合并请求；不得从 `dev_code`、`dev_blueprint`、临时分支或直接提交进入 `main`；
- 未经人工明确要求，智能体不得 checkout `main` 后操作，也不得对其 commit、push、merge、rebase、cherry-pick、reset、force push、删除或修改保护设置；
- 必要的只读检查可以直接针对引用执行，例如 `git show main:<path>`、`git diff main...dev` 或远端状态查询，不为了检查而切换工作分支；
- 人工要求创建 `dev -> main` 合并请求，只授权创建和报告，不授权批准、自动合并或随后手动合并；
- `dev -> main` 必须等待人工审阅并由人工明确决定是否通过。智能体不得以检查通过、无冲突或已有批准为由推定合并权限。

## `dev`：阶段里程碑集成分支

- `dev` 不承担日常功能开发或蓝图讨论，只接收已经形成可部署里程碑的 `dev_code`；
- `dev_code -> dev` 前应具备可直接浏览的页面、当前里程碑承诺的功能集成、可靠降级和部署产物；
- 合并候选至少通过一次 `npm run verify`、构建产物检查和与里程碑相称的人工浏览体验；同一轮不得重复执行已经包含在 `verify` 中的质量或构建门禁；
- 合并到 `dev` 仍需要人工明确授权。进入 `dev` 不代表已经获得 `dev -> main` 的创建或合并权限。

## `dev_blueprint`：蓝图与规划分支

- 允许主动修改正式蓝图、草稿、架构、指南、参考、Agent 规范和必要的文档治理内容；
- 可以读取和检查 `src/`，也可以运行只读 lint、类型检查或构建以理解现状；不得在该分支主动修改 `src/` 的功能、设计或格式；
- lint 或格式检查发现的源码问题应记录并在 `dev_code` 修正，不在 `dev_blueprint` 使用自动修复生成源码差异；
- 可以通过 `dev_code -> dev_blueprint` 的阶段同步接收源码提交；接收源码不等于授权在该分支继续开发源码；
- 若合并出现 `src/` 冲突，不应在 `dev_blueprint` 临时设计新的功能结果。优先中止或暂停合并，在 `dev_code` 基于最新蓝图解决后重新同步；
- 正式蓝图进入下一阶段前，应完成必要的影响定位、追踪检查和草稿生命周期清理，再由人工决定何时同步到 `dev_code`。

## `dev_code`：源码实现分支

- `src/` 的功能、视觉、交互、数据模型、可访问性和非功能性源码修正都在 `dev_code` 产生；
- 开发前先同步已经人工确认的 `dev_blueprint`，再按 active 蓝图和必要的一次性计划实现；不得用候选建议或未采纳创意覆盖正式蓝图；
- 新增、删除或重命名功能源码时，可以并且必须在同一实现中维护 `docs/blueprint/traceability.json`；
- 若实现发现必须改变用户目标、行为契约、状态边界或阶段定义，应停止扩大源码改动，把问题送回 `dev_blueprint` 规划。正式蓝图语义修改默认不在 `dev_code` 发起；
- 完成一个有限切片后，将 `dev_code` 同步回 `dev_blueprint`，使下一轮规划能够依据真实实现；
- 申请进入 `dev` 前，必须再次吸收该轮 `dev_blueprint` 的最终修正，确保候选提交同时包含最新源码和最新正式蓝图。

## 标准同步循环

```text
dev_blueprint 规划并正式化下一阶段蓝图
→ 人工确认蓝图阶段
→ dev_blueprint 合并到 dev_code
→ dev_code 按 active 蓝图实现并验证
→ dev_code 合并回 dev_blueprint
→ dev_blueprint 基于真实实现修正下一轮蓝图
→ dev_blueprint 再同步到 dev_code
→ dev_code 形成可部署里程碑
→ 经人工授权合并到 dev
→ dev 达到阶段发布条件
→ 经人工授权创建 dev -> main 合并请求
→ 人工审核并决定是否合并
```

`dev_blueprint` 与 `dev_code` 的双向同步是有阶段边界的闭环，不应在每个小提交后往返合并。一次同步应对应“蓝图已确认”或“有限源码切片已完成”这样的可解释节点。

## 一次性计划的逐切片闭环

一次性开发计划中的“切片”是该计划定义的最小独立源码交付单位，不等同于每次文件保存、修复提交或任意小改动。计划列出的每个可执行源码切片都必须分别完成以下闭环；只有一个切片时执行一次，存在多个切片时依次执行，计划文件是否在阶段结束后删除不影响本节作为长期规则继续生效。

1. `dev_blueprint` 只批准下一项切片，确认其正式蓝图依据、边界、候选影响路径和验收方式已经明确，并在获得相应 Git 授权后提交、推送计划状态；
2. 按本指南的同步与人工门禁把该状态及最新 active 蓝图同步到 `dev_code`；
3. `dev_code` 只实现当前切片，执行与风险相称的最小检查，并形成至少一个只属于该切片的 Conventional Commit 后推送。同一提交不得同时宣称完成两个或更多计划切片；同一切片确有必要时可以包含多个提交，但这些提交不得夹带下一切片；
4. 当前切片经验证后，按本指南将 `dev_code` 同步回 `dev_blueprint`。蓝图分支复核真实差异与最小完成证据，处理确有必要的蓝图或追踪修正，再把该切片标记为完成；
5. 只有上一个切片已经回到 `dev_blueprint` 并完成状态收口，才能批准和同步下一个切片；所有切片完成后，再执行最终蓝图同步、测试项关闭和一次性计划清理。

若某个切片在实现前被证明无法产生独立可验证的源码结果，应先在 `dev_blueprint` 重划或合并计划切片，不能制造空提交，也不能在 `dev_code` 未经记录地与下一切片合并实现。实现中若发现必须改变产品契约或切片边界，应停止扩大当前源码改动并返回蓝图分支处理。

计划只需要记录切片状态、代码提交或 Pull Request、规定检查是否通过、未验证项和必要的契约影响，不复制完整日志。正在开发这一事实由 `dev_code` 分支和对应 Pull Request 表达，不为重复记录进度增加 Git 往返。本节定义流程；`docs/drafts/plans/README.md` 只定义临时计划的格式和生命周期，各计划不得另写一套相冲突的分支流程。

以上闭环本身不自动授予 commit、push、创建 Pull Request 或合并权限。人工若只批准计划内容，Git 写入仍须另行授权；人工若明确授权按某项已批准计划自动执行至最终切片并回到 `dev_blueprint`，该授权覆盖计划范围内 `dev_blueprint` 与 `dev_code` 之间完整闭环，不需要逐片重新请示。自动执行授权不得扩张到 `dev_code -> dev`、`dev -> main`、部署、发布或计划外工作，具体决策责任边界见 `docs/drafts/plans/README.md`。

## Pull Request 与直接 fast-forward

长期分支之间默认通过 Pull Request 合并，以保留变更说明、审查结论与人工门禁。Pull Request 的可合并状态、检查通过或无冲突只表示技术条件成立，不替代对应阶段的人工授权。

- `dev_code -> dev` 始终使用 Pull Request，因为它是源码进入阶段里程碑集成分支的正式门禁；
- `dev -> main` 始终使用 Pull Request，并在创建请求和最终合并两个节点分别取得人工授权；
- 只有 `dev_blueprint` 与 `dev_code` 之间进行同一开发周期内、已经确认和验证的纯同步时，才可以考虑直接 fast-forward；
- 其他未在分支职责表中允许的方向，不因满足 fast-forward 技术条件而获得合并权限。

直接 fast-forward 必须同时满足以下条件：

1. 来源与目标符合本指南定义的分支职责和同步方向；
2. 工作区干净，并且已经获取相关远端分支的最新状态；
3. 目标分支是来源分支的严格祖先，可由 `git merge-base --is-ancestor <target> <source>` 确认；
4. 差异只包含同一开发周期内已经确认、验证且无需再次审查的同步成果；
5. 不存在冲突、分叉、未处理审查意见或独立阶段门禁；
6. 人工已经明确授权本次直接同步；
7. 来源和目标不属于 `dev_code -> dev` 或 `dev -> main`。

提交数量不能单独决定是否直接 fast-forward：单个提交也可能包含高风险或未经审核的改动，多条提交也可能只是已确认成果的纯同步。任一条件不成立时，改用 Pull Request，不通过 rebase、squash 或 cherry-pick 绕开审查边界。

## 合并策略与历史约束

- 长期分支之间使用 fast-forward 或保留共同祖先关系的正常 merge commit；不得使用 squash merge、rebase 后强推或反复 cherry-pick 代替同步；
- 不对已经共享的长期分支历史进行重写，不使用无条件 force push；
- 同一内容只沿规定方向合并，不通过复制文件、补丁搬运或重新提交制造平行历史；
- 每次 Git 授权都应明确来源分支、目标分支，以及是否只创建请求、是否允许 push、是否允许最终合并。

## 阶段门禁

### 蓝图进入源码开发

- 当前阶段正式蓝图已经人工确认并处于 `active`；
- `blueprint:check` 通过，契约变化已经运行影响定位；
- 已迁移草稿不存在重复正式事实源；
- 本次实现范围已收敛为有限切片，必要时由已批准的一次性计划编排。

### 源码回到蓝图规划

- 有限切片可以构建并完成与风险相称的验证；
- 新增、删除和重命名源码已经更新追踪关系；
- 未实现、失败路径和发现的契约问题已经明确，不把实现缺口伪装为蓝图完成；
- 合并只用于同步真实实现，不在合并冲突中临时扩张产品范围。

### 源码进入 `dev`

- 当前短期里程碑具备展示能力、集成后的功能元素和可部署浏览体验；
- `npm run verify`、构建产物与关键用户旅程通过；
- 最新正式蓝图已同步回 `dev_code`；
- 人工已经确认该里程碑值得进入集成分支。

### `dev` 进入 `main`

- 只创建 `dev -> main` 合并请求；
- 当前阶段达到人工定义的发布里程碑；
- 必要检查、部署预览和人工体验已经完成；
- 最终合并必须再次获得人工明确确认，禁止自动通过。
