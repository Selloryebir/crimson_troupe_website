# Git 分支职责与晋级工作流

## 目的

本文件是仓库长期分支、临时工作分支、允许的合并方向、审核方式和人工门禁的唯一完整说明。它用于隔离正式功能、体验实验、阶段集成和正式发布；所有人员与智能体在创建分支或执行 commit、push、创建合并请求、合并、删除分支前，都必须先确认当前分支及本文件约束。

用户当次明确指令仍然优先，但一次授权只覆盖被明确指定的 Git 操作，不自动扩张为后续 push、合并、删除分支、部署或发布权限。

## 分支模型

长期分支只承担集成成熟度，不承担日常开发：

| 分支       | 核心职责                         | 允许的主要来源 | 允许的主要去向 |
| ---------- | -------------------------------- | -------------- | -------------- |
| `main`     | 人工审核后的稳定发布主线         | 仅 `dev`       | 无             |
| `dev`      | 可部署、可浏览的阶段里程碑候选   | 仅 `dev_code`  | `main`         |
| `dev_code` | 正式蓝图与已批准实现的滚动集成线 | 获准工作分支   | `dev`          |

日常工作从最新且已经确认的 `dev_code` 基线创建一个目标有限的临时分支：

| 分支模式                | 核心职责                                 | 能否直接进入 `dev_code`                          |
| ----------------------- | ---------------------------------------- | ------------------------------------------------ |
| `dev_feature_<slug>`    | 人工明确提出、先批准蓝图再实现的正式功能 | 完成正式蓝图、实现、验证与人工合并授权后可以     |
| `dev_experiment_<slug>` | 依据创意案制作隔离原型并验证体验假设     | 只有创意及代码都获认可并完成正式化与清理后可以   |
| `dev_<lane>_<slug>`     | 未来经人工建立的专业工作通道             | 只有该通道已定义审核门禁且当前成果通过门禁后可以 |

`<slug>` 使用稳定、可理解的 ASCII 名称；每个分支只服务一个可以独立审核、晋级或废止的目标。`dev_art_<slug>` 可以作为未来艺术通道的命名，但名称本身不授予写入范围或合并资格；启用新通道前必须由人工确认其职责、允许内容、审核人、验收证据、晋级条件和废止方式，并同步更新本文件与 `AGENTS.md`。

分支隔离不改变文件职责。正式蓝图仍只位于 `docs/blueprint/`，未采纳材料仍只位于 `docs/drafts/`，运行时内容和源码仍按仓库结构存放。

## 固定晋级方向

```text
dev_feature_<slug> ──────┐
dev_experiment_<slug> ───┼─ 经各自审核与人工授权 ─→ dev_code
dev_<lane>_<slug> ───────┘

dev_code ── 里程碑 Pull Request ─→ dev ── 发布 Pull Request ─→ main
```

- 工作分支不得绕过 `dev_code` 直接进入 `dev` 或 `main`；
- `dev_code` 与 `dev` 在 Git 上长期并存，但职责上是滚动集成到阶段候选的单向晋级关系，不是互相开发的平行分支；
- 未经人工明确授权，不得把检查通过、无冲突、原型可运行或 Pull Request 可合并解释为晋级许可；
- `dev_code` 默认不直接产生普通功能、创意原型或艺术探索；必要的集成修复也应优先建立范围有限的工作分支。

## `dev_feature_<slug>`：正式功能分支

正式功能分支把“蓝图确认”和“源码实现”放在同一个有限分支中，但必须保持先后门禁：

1. 从最新且已确认的 `dev_code` 创建分支，记录本次目标、非目标和相关 active 蓝图；
2. 需要新产品契约时，先在 `docs/drafts/blueprint/` 提出候选，或对现有蓝图给出明确修改案；
3. 人工确认目标、访客结果、行为边界和验收条件后，按草稿迁移规则写入 `docs/blueprint/`，运行 `blueprint:impact` 和 `blueprint:check`，必要时同步追踪表；
4. 只有正式蓝图已经在当前分支生效，才能开始对应源码实现；蓝图批准前不得预做会固化其中一种产品答案的功能代码；
5. 在同一分支按已批准计划完成有限实现切片，每个切片形成独立可观察结果和独立提交；
6. 完成与风险相称的质量、构建、浏览器及独立审查，清理已经迁移的一次性草稿和计划；
7. 经人工授权创建并合并 `dev_feature_<slug> -> dev_code` Pull Request。

纯内部修复若不改变产品契约，可以省略新蓝图草稿，但仍应通过目标有限的 `dev_feature_<slug>` 或未来经批准的修复通道完成。实现中若发现必须改变已经批准的产品结果，应停止受影响的源码扩张，在同一分支回到草稿与人工门禁；技术困难本身不要求另建规划分支。

## `dev_experiment_<slug>`：创意实验分支

创意实验用于仅凭语言无法可靠判断体验、艺术或叙事效果的候选。新建或实质修改创意草稿、为其制作运行时原型及补充专属研究资料，应在对应 `dev_experiment_<slug>` 进行；它们不得先进入 `dev_code` 形成未批准的正式事实。

每项实验至少记录：体验假设、适用范围、非目标、实验基线、预期玩家所得、首次与重复体验时长、验证场景、停止条件、已知缺口、权利与无障碍边界。实验可以由一个智能体或范围互不冲突的智能体集群开发，但实现者不得把自己的结论称为独立审查；独立 Reviewer 只报告证据和高置信问题，最终由人工体验并决定：

- **废止：** 不向 `dev_code` 合并；保留必要审查证据后遗弃分支。删除本地或远端分支仍须人工明确授权；
- **继续修改：** 只在原实验目标内迭代；若目标实质变化，应更新实验假设或新建分支，不用无限扩张的原型替代决策；
- **只采纳创意：** 把认可结论转入新的 `dev_feature_<slug>`，按正式功能流程重新蓝图化和实现；原实验代码不合并；
- **采纳创意与代码：** 在原实验分支将稳定目标迁入正式蓝图，删除失败变体、调试入口、临时状态和重复草稿，补齐追踪、质量与浏览器验证，再经人工授权通过 Pull Request 进入 `dev_code`。

实验预览只用于隔离验证，不构成正式发布，不加入稳定站点导航、正式内容根或搜索索引。实验分支仍须遵守隐私、安全、素材权利、可靠退出和基本可访问性边界，不因最终可能废止而获得豁免。

## 未来专业工作通道

艺术、音频、本地化或其他未来能力可以采用 `dev_<lane>_<slug>`，但必须继续服从“工作分支 → `dev_code` → `dev` → `main`”的唯一晋级主干。建立通道时至少明确：

- 它解决的独立变化原因，以及为什么 `dev_feature_*` 或 `dev_experiment_*` 不足以承担；
- 可以主动修改的文件和不得修改的中央入口；
- 输入基线、产物资格、素材权利和自动化或人工验收方式；
- 是否允许并行智能体、谁负责独立审查、哪些决定必须由人工作出；
- 成果进入 `dev_code` 前的正式蓝图、追踪、清理和失败回退要求。

新通道不是新的发布主线，也不得直接向 `dev` 或 `main` 合并。

## `dev_code`：滚动集成分支

- `dev_code` 保存当前集成基线：active 蓝图、追踪关系、已批准源码和已接受文档必须彼此一致；
- 只接收完成对应门禁的工作分支，不接收尚待人工判断的创意、半成品原型或仅因技术上可合并的代码；
- 工作分支进入后运行与跨模块风险相称的集成检查，发现问题应在新的有限工作分支修复，不把 `dev_code` 变成无隔离的日常编辑区；
- 一个实验的创意获批不等于其代码获批；只有“采纳创意与代码”路线可以在清理后从原实验分支晋级；
- 形成可部署里程碑前，确认当前正式蓝图、源码、内容资格、失败路径和追踪表没有被并行合并破坏。

## `dev`：阶段里程碑候选

- `dev` 不承担日常功能开发、蓝图讨论或实验验证，只接收已经形成可部署里程碑的 `dev_code`；
- `dev_code -> dev` 前应具备可直接浏览的页面、当前里程碑承诺的功能集成、可靠降级和部署产物；
- 合并候选至少通过一次 `npm run verify`、构建产物检查和与里程碑相称的人工浏览体验；同一轮不得重复执行已经包含在 `verify` 中的质量或构建门禁；
- 合并到 `dev` 仍需要人工明确授权。进入 `dev` 不代表已经获得 `dev -> main` 的创建或合并权限。

## `main`：人工控制的稳定主线

- `main` 只接受来源为 `dev` 的合并请求；不得从 `dev_code`、任何工作分支或直接提交进入 `main`；
- 未经人工明确要求，智能体不得 checkout `main` 后操作，也不得对其 commit、push、merge、rebase、cherry-pick、reset、force push、删除或修改保护设置；
- 必要的只读检查可以直接针对引用执行，例如 `git show main:<path>`、`git diff main...dev` 或远端状态查询，不为了检查而切换工作分支；
- 人工要求创建 `dev -> main` 合并请求，只授权创建和报告，不授权批准、自动合并或随后手动合并；
- `dev -> main` 必须等待人工审阅并由人工明确决定是否通过。

## 一次性计划的逐切片规则

一次性计划中的“切片”是最小独立源码交付单位，不等同于每次文件保存或任意小提交。计划在所属 `dev_feature_<slug>` 中编写、批准、执行和清理；实验尚未获准正式化时不得用已批准计划的名义绕过实验审核。

1. 人工只批准下一项切片，确认正式蓝图依据、边界、候选影响路径和验收方式明确；
2. 智能体只实现当前切片，执行与风险相称的最小检查，并形成至少一个只属于该切片的 Conventional Commit；
3. 当前切片经验证并在计划内标记完成后，才能开始下一切片；不得用一个代码提交同时完成多个计划切片；
4. 若实现必须改变产品契约或切片边界，停止受影响工作并回到同一功能分支的草稿与人工门禁，不制造空提交，也不把问题转嫁给 `dev_code`；
5. 所有切片完成后执行最终蓝图、追踪、测试项和计划清理，再申请合入 `dev_code`。

计划批准不自动授予 Git 写入。人工若明确授权在具名工作分支按已批准计划自动执行至最终切片，该授权只覆盖明确说明的 commit、push 和 Pull Request 创建范围；是否允许合入 `dev_code`、继续晋级 `dev`、进入 `main` 或部署，仍以授权原文为准。具体决策责任见 `docs/drafts/plans/README.md`。

## Pull Request、同步与历史约束

- `dev_feature_<slug> -> dev_code`、获准的 `dev_experiment_<slug> -> dev_code` 及其他专业工作分支晋级均使用 Pull Request；
- `dev_code -> dev` 始终使用 Pull Request；
- `dev -> main` 始终使用 Pull Request，并在创建请求和最终合并两个节点分别取得人工授权；
- Pull Request 的检查通过、无冲突或可合并状态只表示技术条件成立，不替代人工授权；
- 工作分支需要吸收较新的 `dev_code` 时，可以在获得相应 Git 授权后 fast-forward 或正常 merge；已经共享的工作分支不得通过 rebase 后强推改写历史；
- 晋级合并保留共同祖先和审查历史，不使用 squash、历史重写或反复 cherry-pick 绕开切片、来源与审查边界；
- 同一内容只沿规定方向合并，不通过复制文件、补丁搬运或重新提交制造平行历史；
- 每次 Git 授权都应明确来源、目标，以及是否只允许创建请求、是否允许 push、合并或删除来源分支。

## 阶段门禁

### 正式功能进入源码实现

- 人工已经确认当前工作分支的目标、边界与验收条件；
- 当前阶段正式蓝图已经迁入并处于 `active`；
- `blueprint:check` 通过，契约变化已经运行影响定位；
- 已迁移草稿不存在重复正式事实源；
- 实现范围已收敛为有限切片，必要时由已批准的一次性计划编排。

### 工作分支进入 `dev_code`

- 来源分支类别、目标和实际差异一致；
- 正式蓝图、源码、追踪关系与草稿生命周期已经闭合；
- 实现、失败路径、窄屏、键盘和减少动态效果按实际风险验证；
- 实验成果另有人工“采纳创意与代码”的明确结论，且实验残留已经清除；
- 独立审查问题已经解决或明确记录为不阻塞风险；
- 人工明确授权创建和最终合并该 Pull Request。

### `dev_code` 进入 `dev`

- 当前短期里程碑具备展示能力、集成后的功能元素和可部署浏览体验；
- `npm run verify`、构建产物与关键用户旅程通过；
- 当前正式蓝图、内容资格与实现保持一致；
- 人工已经确认该里程碑值得进入阶段候选。

### `dev` 进入 `main`

- 只创建 `dev -> main` 合并请求；
- 当前阶段达到人工定义的发布里程碑；
- 必要检查、部署预览和人工体验已经完成；
- 最终合并必须再次获得人工明确确认，禁止自动通过。

## `dev_blueprint` 退役迁移

`dev_blueprint` 不再属于目标分支模型。采用本流程后不得继续在其上开启新的规划、功能或实验事项，但退役不授权直接删除或丢弃现有内容：

1. 只读比较本地及远端 `dev_blueprint` 与 `dev_code`，列出独有提交、未提交修改和未跟踪文件；
2. 已批准且仍有效的正式蓝图、工程规范或实现成果，通过符合新职责的 `dev_feature_<slug>` 进入 `dev_code`；
3. 尚未采纳的创意草稿及其专属研究、原型进入对应 `dev_experiment_<slug>`，不得借退役过程自动获得正式效力；
4. 被废止或重复的内容由人工逐项决定是否遗弃，不用宽泛 stash、reset、clean、历史重写或批量复制处理；
5. 只有 `dev_blueprint` 已无独有有效成果、相关工作分支均有明确去向且工作区干净后，才能在人工明确授权下删除本地或远端分支。

迁移期间允许在 `dev_blueprint` 完成本次分支治理规范及其一致性修正；除此之外不再把它作为新任务的目标分支。
