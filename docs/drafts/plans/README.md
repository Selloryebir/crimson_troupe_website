# 一次性开发计划

本目录保存为有限开发事项编排实施顺序的临时计划。计划可以经人工批准执行，但只能组织正式蓝图已经允许的工作，不能产生或覆盖产品契约。

每份计划使用 `docs/drafts/README.md` 规定的 `PLAN-*` 固定字段和执行切片表。源码切片必须遵守 `docs/guides/git-branch-workflow.md` 的“逐切片闭环”，计划只声明本阶段切片、依赖和验收，不复制或改写长期分支流程。

切片状态只使用“待开始”“已批准待同步”“已完成”，任一时刻最多一个切片处于“已批准待同步”。每项源码切片必须有独立可观察结果，并至少对应一个不与其他切片共用的 `dev_code` 提交；必要的同切片修复可以追加提交，但下一切片必须等待当前切片回到 `dev_blueprint` 并完成状态收口后才能开始。若预期工作不能形成独立源码结果，应在执行前重划切片，不制造空提交。

## 自动执行授权与决策责任

批准计划内容只表示切片边界和执行顺序可以采用，不自动授予 Git 写入。人工明确授权“按已批准计划自动执行至最终切片并合并回 `dev_blueprint`”或同等范围时，智能体应连续执行 `docs/guides/git-branch-workflow.md` 规定的全部逐切片闭环；该授权覆盖计划范围内 `dev_blueprint` 与 `dev_code` 之间必要的 commit、push、Pull Request 创建和合并，不为每个切片或技术步骤重复申请确认。授权不延伸到 `dev_code -> dev`、`dev -> main`、部署、发布、计划外功能或产品契约变更。

决策归属不按“是否困难”划分，而按“是否改变已经获得人工确认的产品结果”划分：

- 智能体负责在 active 蓝图、已批准计划和验收条件内选择实现手段，包括数据结构、组件边界、算法、类型设计、等价重构、缺陷修复、性能与可访问性修正、明确允许的预览用 AI 翻译、质量流水线、浏览器验证和不改变交付结果的切片细化。存在多个同等合规方案时，选择改动最小、风险最低且易于验证的方案，不把普通技术取舍上交人工；
- 人工负责会改变产品目标、范围、访客可感知行为、UX 路线、艺术风格、叙事与设定取舍、内容采纳或删除、正式翻译认可、发布范围、阶段优先级、验收标准，或要求偏离 active 蓝图的选择。智能体可以给出专业分析和推荐结论，但不得先实施其中一种再要求人工追认；
- 一个技术问题只有在可行方案会产生上述不同产品结果，且正式蓝图、已确认草稿和计划都无法唯一决定时，才升级为人工决策。技术困难、检查失败、环境问题或可以在既定契约内修复的实现缺陷，本身不构成人工介入理由。

蓝图草稿研讨应尽量在开发前用 `OPEN-*` 暴露并解决主观产品选择。自动执行开始前不得遗留会影响实现方向的未决 `OPEN-*`；已有验证方法和关闭切片的 `TEST-*` 可以随计划执行。执行中若新发现必须由人工决定的事项，只暂停受其影响的切片或依赖路径，先完成仍然独立且不预设答案的安全工作，再以“证据、影响、可选方案、推荐结论”提出一次集中问题。人工答复后按蓝图和草稿门禁处理，不把该极端边界变成频繁确认流程。

计划完成、取消或被替代后，将仍有长期价值的产品或工程规则迁入其正式责任目录，再删除计划文件；分支流程本身已经由长期指南保存，不需要从计划迁移。本目录不保存长期路线图、进度流水账或重复测试日志。
