# 草稿工作区

`docs/drafts/` 集中保存临时且不构成正式产品事实源的材料，包括尚未获得人工采纳的蓝图、建议与创意草稿，以及获准执行但完成后应删除的一次性开发计划。这里的内容不直接约束产品或源码，也不属于 `docs/blueprint/traceability.json` 的追踪对象。

## 目录职责

```text
docs/drafts/
├── README.md
├── blueprint/
│   └── README.md       # 蓝图草稿职责与 SET-* 模板
├── recommendations/
│   └── README.md       # 建议草稿职责与 REC-* 模板
├── creative/
│   └── README.md       # 创意草稿职责与 CRE-* 模板
└── plans/
    └── README.md       # 一次性计划职责与 PLAN-* 模板
```

- `blueprint/` 可以从头搭建新蓝图，也可以针对现有正式蓝图提出修改；正文中的单项结论可以已经过讨论确认，但整份草稿在人工明确要求正式迁移前仍不是正式蓝图，具体格式见 [`blueprint/README.md`](blueprint/README.md)；
- `recommendations/` 保存更宏观的候选建议，例如下一步考虑什么、为什么值得做以及最小如何落地，不因优先级或写入正文而自动获得效力，具体格式见 [`recommendations/README.md`](recommendations/README.md)；
- `creative/` 保存尚未采纳的文案、叙事蓝本、表现概念和内容创意，具体格式见 [`creative/README.md`](creative/README.md)；
- `plans/` 保存一次性开发计划；计划即使获准执行，也只能编排已经批准的工作，不能覆盖正式蓝图或产生新的产品决策，具体格式见 [`plans/README.md`](plans/README.md)；
- 普通功能开发只读取正式蓝图。只有任务涉及规划、草稿评审、已获授权的一次性计划、正式迁移，或用户明确指定草稿时，才读取本目录。

四个子目录的 `README.md` 是长期职责与格式入口，不属于随阶段完成而删除的草稿。清理最后一份实际草稿时保留对应 README，使目录职责在 Git 中持续存在。

草稿内容获人工采纳后按责任迁移：

- 稳定目标、行为契约和内容规则进入 `docs/blueprint/`；
- 内容结构、叙事规则和文案边界进入 `docs/blueprint/content/`；
- 实际展示的完整文案进入 `src/data/` 或未来唯一的 `src/content/`，运行时素材进入 `src/assets/`；
- 外部依据进入 `docs/references/`，工程事实进入 `docs/architecture/`；
- 迁移完成后删除草稿中的来源正文，避免形成多个权威来源。

## 固定文档骨架

除目录说明文件 `README.md` 外，每份蓝图、建议、创意草稿和一次性开发计划都必须在标题和固定元数据后使用以下三个顶层部分：

```markdown
## 正文

## 待解决问题

## 正式拆分与影响定位
```

元数据固定为以下字段；没有内容时明确写“无”或“原稿未说明”，不能省略字段并期待人员或智能体从自然语言中推断：

```markdown
- 文档类型：
- 状态：
- 规划效力：
- 分析基线：
- 目的：
- 非目标：
```

可以增加确有必要的类型专用元数据，但不能删改固定字段。正文对象的固定子标题必须带所属 ID，例如 `REC-01 原因`，避免同一文件产生重复标题和不稳定锚点。跨类型公共维护规则只在本文件保存，不在各子目录重复。

### 类型专属格式

创建或修改草稿前，除本文件外还须阅读对应子目录 README。类型专属字段和正文模板只在所属目录维护：

| 草稿类型       | 唯一格式入口                                             | 正文对象 |
| -------------- | -------------------------------------------------------- | -------- |
| 蓝图草稿       | [`blueprint/README.md`](blueprint/README.md)             | `SET-*`  |
| 建议草稿       | [`recommendations/README.md`](recommendations/README.md) | `REC-*`  |
| 创意草稿       | [`creative/README.md`](creative/README.md)               | `CRE-*`  |
| 一次性开发计划 | [`plans/README.md`](plans/README.md)                     | `PLAN-*` |

### 待解决问题

问题使用以下固定结构：

```markdown
### OPEN-01｜问题名称

- 状态：待回答 / 已回答，待人工确认
- 所属规划或关联正文：
- 问题：
- 影响：
- 建议答案：
- 合并动作：
```

- `OPEN-*` 用于仍需人工选择的事项；建议草稿产生独立问题时使用 `REC-OPEN-*`，创意草稿使用 `CRE-OPEN-*`，避免不同草稿混淆；
- `TEST-*` 只用于方向已经明确、但参数必须由可部署版本验证的事项；
- 智能体可以分析并填写建议答案，但不能自行把答案提升为正文；
- 人工明确要求“确认并合并到正文”后，才修正唯一正文并立即删除对应 OPEN/TEST 项；
- 若新结论与正文冲突，直接修正原正文及引用，不并列保留新旧说法。

### 正式拆分与影响定位

该部分只回答“确认后应检查和迁入哪里”，不复制正文。固定使用：

| 来源 ID                     | 目标位置                        | 影响性质               | 确认后的动作             |
| --------------------------- | ------------------------------- | ---------------------- | ------------------------ |
| `SET-*` / `REC-*` / `CRE-*` | 仓库根目录相对路径或正式蓝图 ID | 新增、修正、替代、删除 | 迁移、核对并删除草稿来源 |

定位表表示需要判断的候选影响范围，不要求每个目标都产生修改。蓝图与源码的最终关系仍只维护在 `docs/blueprint/traceability.json`。

结构化内容迁移时，定位粒度必须跟随对象结构：表格优先复用业务主键或来源 ID，流程核对稳定状态与关键转移，分项档案核对实体 ID；不为句子或单元格另造永久编号。迁移只核对对象身份是否都有落点、对象关系是否保留、迁移后是否只有一个正式责任方。可机械比较的键集合只执行一次对照，不生成常驻覆盖报告；艺术语义按既有必要字段核对，不重复全文摘要。

## 单向生命周期与人工门禁

内容草稿遵循以下循环：

```text
提出问题
→ 给出建议答案
→ 人工确认并要求融入正文
→ 删除已解决问题
→ 继续提出和解决问题
→ 人工明确提出正式迁移
→ 按影响定位拆入正式文件
→ 核对迁移完整性
→ 删除已迁移的草稿正文与定位
```

存在两个相互独立的人工门禁：

1. **融入草稿正文：** 只改变临时材料，不授权修改正式蓝图或源码；
2. **正式迁移：** 只有人工明确提出迁移或合并请求后，才允许修改正式规划文件。

建议草稿中的内容可以先进入蓝图或创意草稿，也可以在边界已经成熟且人工明确要求时直接进入正式文件。候选建议不会仅因优先级为 `P0` 自动获得效力。人工批准一次性开发计划只确认计划内容，不授权计划自行修正产品契约；是否同时授权完整自动执行及其 Git 操作，以人工当次明确指令和 `plans/README.md` 的边界为准。

## 正式蓝图状态与迁移

`docs/blueprint/` 中的所有蓝图都是正式蓝图，只允许以下状态：

- `active`：启用，是当前有效的正式约束；
- `retired`：终止，不再约束开发。

正式蓝图不使用 `draft` 状态。蓝图草稿获人工采纳后，新增蓝图默认以 `active` 注册，对既有蓝图的修改默认保持 `active`，除非人工明确要求终止。蓝图被新 ID 替代时，在同一次迁移中将旧蓝图设为 `retired`，并移除或重定向它的依赖与源码映射；不得让两个启用蓝图同时拥有同一正式事实。

## 正式迁移与删除规则

正式迁移在同一次完整改动中依次完成：

1. 根据职责将选定正文拆入目标文件；
2. 核对目标文件完整保留原意，没有把 OPEN/TEST 当成既定契约；
3. 更新必要的蓝图依赖、文档索引和 `docs/blueprint/traceability.json`；
4. 检查正式文件之间不存在相反表述或重复事实源；
5. 删除已经成功迁移的正文项及其定位行，不保留“已迁移摘要”；
6. 对仍留在草稿中的问题和正文重新确认引用有效。

只有同时满足以下条件时才删除整份内容草稿：

- 正文已经全部迁移、拒绝或作废；
- 不存在仍有效的 OPEN/TEST 项；
- 不存在尚未完成的拆分定位。

正文为空但仍有待解决问题时，草稿继续保留；也可以先把问题无损移交给另一份有效草稿，再删除空文件。Git 保存历史，不另建决策档案或迁移日志。

本节的“草稿”只指各子目录中的实际提案或计划文件，不包括子目录 `README.md`。目录 README 只有在目录职责被正式取消并同步修正全部引用时才可删除。

## 路径与维护边界

- 草稿文件名使用小写英文 kebab-case，目录已经表达草稿属性时不再添加 `-draft` 后缀；
- 文中涉及仓库文件时统一使用仓库根目录相对路径，例如 `docs/blueprint/modules/search.md`，不依赖草稿当前目录推导；
- 草稿之间通过完整路径和稳定 ID 引用，不复制正文；
- 移动草稿时同步检查本目录入口、`docs/README.md`、`docs/blueprint/README.md`、架构说明和 Agent 规则；
- 不为普通讨论增加状态数据库、审批表、迁移清单或自动化门禁；固定格式出现真实漂移前，不新增专用校验工具。
