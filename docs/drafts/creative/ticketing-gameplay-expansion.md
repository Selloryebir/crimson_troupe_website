## 正文

### CRE-03｜现状诊断与拓展目标

- 状态：候选，待人工判断
- 内容类型：玩法诊断与体验目标
- 适用时间层：表站“现在”；只分析与里站的候选内容关联，不共享运行时状态
- 内容目的：解释当前功能完整但重玩动力不足的原因，并给后续候选建立统一判断标准
- 预期入口：现有表站 `/tickets/` 与 `/tickets/partner/` 流程
- 设定边界：不把降低成功率、增加等待、堆叠结局或隐藏更多信息误当作可玩性
- 正式迁入目标：人工采纳后判断 `BP-FND-EXPERIENCE`、`BP-MOD-TICKETING` 与 `BP-QLT-STAGES`

#### CRE-03 内容正文或叙事蓝本

当前票务小游戏已经具有完整的“事务外壳”：七个可售场次、真实逐场分区与价格、可视化场馆、跨国家版本票篮、水稻网处理、跳楼机加价与挽留、七种 Ending、失败记录、三次后保底、凭单和逐场可下载／打印纪念票。问题不在内容量不足，而在玩家选择与过程结果之间的联系太弱。

| 现有机制                                  | 实际形成的动态                                                                   | 可玩性问题                                                                       | 应保留的价值                                   |
| ----------------------------------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- | ---------------------------------------------- |
| 选择最多七个场次与逐场分区                | 改变总价、凭单和票面；不改变事件、路线或基础概率                                 | 更接近配置表单；一次把七场全部入篮即可批量取得全部节目票                         | 真实内容、场馆差异、多场次票篮和唯一价格事实源 |
| 普通线路首轮 `32 / 36 / 32` 概率          | 直接成功会跳过大部分分支；网络波动只要求重试；只有不可用结果立即展示跳楼机三岔路 | 最有趣内容被随机门槛挡住，玩家不能主动选择“这局想研究什么”                       | 有限不确定性和不伪造确定库存的叙事             |
| 跳楼机 `150% / 148% / 58%` 路线           | 形成接受、拒绝、挽留和失败记录                                                   | 第一次体验有讽刺性，复玩后主要剩下“是否多付钱”的二元选择                         | 平台身份、透明金额、明确拒绝和返回路径         |
| 网络不连续、最多三次后普通成功            | 坚持提交最终必定结束                                                             | 防挫有效，但没有可学习的资源与选择时，会退化为重复点击等待保底                   | 明确时间上限和可靠收束                         |
| `endingHistory`、`journeyTags` 与组合印章 | 失败、拒绝、回流和人工复核已经进入最终票面                                       | 旅程含义在成功前不可见，成功后也缺少清楚复盘；玩家难以意识到票面记录了自己的路线 | 已有稳定状态、视觉构件和用户可带走的纪念物     |
| 新一轮清空、标签页关闭即结束              | 不追踪用户，也不形成永久购买或收藏档案                                           | 符合隐私边界，但传统“图鉴式”长期收集不成立                                       | 无账号、无长期画像、易清除、跨国家版本状态安全 |

依据 MDA 和自主／胜任感研究，本轮候选先确定四种目标体验，再反推机制：

1. **互动性：** 玩家在第一次概率结果之前就能作出至少一项会改变后续选项的决定；
2. **趣味性：** 每局只出现少量高密度票务插曲，玩家读懂信息、比较代价并留下自己的处理路线；
3. **可重复性：** 随机负责重排“遇到什么问题”，玩家负责决定“怎样处理”；下一局探索另一种策略，不是继续点击同一按钮抽取低概率内容；
4. **收集感与隐喻性：** 票面、印章与受理记录保存“系统怎样试图编排玩家、玩家怎样即兴离开脚本”，而不是只奖励最终成功。

一局必须独立成立：只玩一次也获得完整结果，不用先失败、不用理解官方设定、不用补齐收藏、不用进入里站。复玩提供的是新的取舍、过程解释和可控物件差异，不把第一局做成残缺教程。

#### CRE-03 素材与实现提示

- 不新增总体分数、等级、战斗、技能树、虚拟货币或角色属性；网页小游戏的优势是短文本判断、真实场次数据、视觉票面和可逆选择。
- 不增加第八或第九个 Ending。继续把 Ending 当“结果层”，另以受理偏好、插曲选择和旅程标签表达“为什么得到这个结果”。
- 不通过延长 `1.7` 秒处理动画、加入无限队列或无差别降低每轮成功概率延长游玩时间；允许在实验中单独压低首轮直达成功率以暴露既有分支，但后续重试与三次保底不能随之拖长。
- 所有候选随机在本轮开始时锁定并随会话恢复；刷新、重复点击、动画进度和国家版本切换不能重新抽取。
- 当前七场可售内容继续来自构建快照，分区和价格继续只读取 `TicketOffer`；候选玩法不得建立平行票价、库存或场次注册表。

### CRE-04｜推荐主玩法：“票务夜·三幕受理”

- 状态：候选，推荐作为主方向
- 内容类型：短局流程、玩家选择与状态结构
- 适用时间层：表站“现在”
- 内容目的：把现有“选票—等待—读结果”改为一轮有目标、有两次取舍、有结果复盘的短流程
- 预期入口：仍从 `/tickets/` 建立票篮并进入 `/tickets/partner/`；不增加主导航入口
- 设定边界：表站仍先是可信票务服务；“三幕”是内部设计结构，不要求访客界面反复使用游戏术语
- 正式迁入目标：人工采纳后修正 `BP-MOD-TICKETING` 的状态、处理节拍、分支、票面和验收，并检查 `BP-FND-EXPERIENCE`

#### CRE-04 内容正文或叙事蓝本

推荐结构不是另做一款游戏，而是在现有流程中建立三幕：

```text
第一幕：定调
选择场次与分区 → 选择本轮受理偏好 → 查看后果摘要

第二幕：候场
锁定本轮条件 → 处理 1 个预检插曲 → 执行一次既有概率结果
→ 如未终止，再处理 1 个与实际分支匹配的插曲

第三幕：落印
沿用七种 Ending 收束 → 显示路线受理簿
→ 成功时选择票坊后整理 → 生成既有凭单与逐场纪念票
```

#### 第一幕：定调

用户完成现有票篮后，从三项“受理偏好”中选一项。它们不是人物身份、职业或人格测试，只是本轮事务优先级：

| 稳定候选 ID                | 访客可理解语义 | 明示承诺                                                                                | 后续差异                                                                                                             |
| -------------------------- | -------------- | --------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `PREF_FACE_VALUE`          | 票面价优先     | 优先保留原价；任何正向差额仍需再次明确接受                                              | 不屏蔽跳楼机，但先提供来源与费用复核；普通渠道不可用时优先出现分批放票／回流选择；结算记录是否实际守住原价           |
| `PREF_EXACT_ZONE`          | 原席区优先     | 不自动改区；同等级多区域仍是同一个 `TicketZone`，不会伪造逐座库存                       | 不生成静默替代；不可用时提供保留原区重试、返回票篮或查看其他线路；若最终改区，必须由用户重新确认并记录偏好发生变化   |
| `PREF_FLEXIBLE_ATTENDANCE` | 成行优先       | 可为已选场次预先指定一个同场实际 `TicketOffer` 作为候补；候补只是选项，不自动入篮或结算 | 出现确认回流时可以逐项接受候补分区；金额、分区和最终票面同步更新；多场次仍逐项确认，不用一个全局开关替用户修改全部票 |

偏好选择区同时说明：“偏好会改变本轮可见处理选项，不保证库存，也不会自动接受加价或改区。”用户可在离开官网票篮前更改；进入水稻网后偏好冻结，返回票篮才可重选。

#### 第二幕：候场

进入水稻网时生成并冻结一个语言无关 `runSeed`，据此从合格插曲中选择至多两项：

1. **预检插曲：** 在第一次结果抽取前出现，让玩家从一开始就有选择；
2. **分支插曲：** 只在网络、不可用、优先报价、回流或人工复核等真实状态出现；
3. **终局整理：** 只改变复盘和票面印制，不重新抽取结果。

预检完成后仍执行一次提交一次抽取。当前实验把普通线路首轮从 `32%` 成功、`36%` 不可用、`32%` 网络调整为 `12%` 成功、`56%` 不可用、`32%` 网络，让多数首轮进入已有处理分支；后续普通重试仍为 `32 / 36 / 32`，优先线路仍为 `58%` 成功，三次需重提结果后的可靠收束不变。第一版不因“答题正确”暗中提高概率。若后续实测证明选择对结果影响不足，再单独评审少量、完全明示的确定性转换，例如“接受已确认回流的候补分区即按该分区普通成功”；不能通过隐蔽概率修正制造伪策略。

插曲必须满足以下最低条件：

- 每项最多提供三个动作，且至少两个动作会改变渠道、金额、分区、继续路径、处理记录或票面语义中的一项；
- 任何不可逆后果在按钮前说明；颜色、显著度和焦点不替代文字；
- 选择结果立即进入“路线受理簿”，不能只换下一段随机文案；
- 不要求外部设定知识、记忆上一屏文字、快速反应、拖拽、精准点击 SVG 或反复提交；
- 每局通常只处理两个插曲，保底收束可以增加一个不超过 `20` 秒的确认步骤，但不能无限增长。

#### 第三幕：落印

现有七种 Ending 保持闭集。成功后在凭单前先显示“路线受理簿”，用当前国家版本的运营语言回答：

- 本轮选择了哪一项受理偏好；
- 实际经历了哪些状态与决定；
- 最终渠道、原始票款、全部差额和应付合计；
- 是否发生改区、回流、人工复核、拒绝或优先线路失败；
- 哪些实际经历进入组合印章。

受理簿只列出本轮发生的项目，不显示内部 Ending ID、概率、稀有度、总收集数或未经历空位。随后成功用户从两到三项“票坊后整理”中选一项，决定无文字的纸边、套印或票钳表现；这项选择与 Ending 组合印章职责分开，同一多场次结果对全部票保持一致。

#### 单局时间预算

| 阶段             | 首次目标时间      | 熟练复玩目标        | 主要操作                                     |
| ---------------- | ----------------- | ------------------- | -------------------------------------------- |
| 票篮与受理偏好   | `60–120` 秒       | `20–45` 秒          | 场次、分区、可选候补、受理偏好               |
| 预检插曲         | `20–40` 秒        | `10–20` 秒          | 阅读两种来源或库存处理方式并选择             |
| 既有平台处理     | `1.5–3` 秒        | `1.5–3` 秒          | 有限处理节拍，不要求输入                     |
| 分支插曲         | `30–90` 秒        | `15–45` 秒          | 原价、原区、候补、优先线路、复核或返回的取舍 |
| 受理簿与票面整理 | `45–90` 秒        | `20–45` 秒          | 复盘路线、选择印制处理、查看／下载／打印票   |
| **整轮**         | **约 `4–6` 分钟** | **约 `1.5–3` 分钟** | 一次成立；熟练后可迅速换偏好或场次重新体验   |

超出六分钟的额外内容必须是用户主动打开的复盘、跨板块链接或票面检视，不把所有人困在长流程中。用户随时可以返回票篮或表站；关闭对话框不清空状态，开始新一轮才按批准后的生命周期处理。

#### 候选状态模型

在现有 `basket / attempt / result` 三层上只增加必要的语言无关结构：

| 字段候选           | 类型方向                                 | 责任                                                 |
| ------------------ | ---------------------------------------- | ---------------------------------------------------- |
| `runSeed`          | 有限整数或短字符串                       | 冻结插曲顺序与装饰变体；刷新和切国家版本不变         |
| `preferenceId`     | 三项闭集                                 | 记录本轮优先级，不推断用户人格                       |
| `fallbackZones`    | `performanceId -> TicketZone` 的可选映射 | 只引用同场真实报价；最终采用前必须再次确认           |
| `incidentHistory`  | 有序 `incidentId`                        | 记录实际出现的插曲                                   |
| `choiceHistory`    | 有序 `choiceId`                          | 记录用户实际动作；显示文案由当前国家版本解析         |
| `artifactFinishId` | 两到三项印制处理闭集或 `null`            | 成功后冻结用户主动选择；不改变票面事实和 Ending 印章 |

状态不保存本地化字符串、倒计时、人物画像、现实日期、浏览器语言、账号、支付或身份资料。新增状态版本安全重置旧结构，不能为开发中间态积累长期兼容分支。

#### CRE-04 素材与实现提示

- 多场次能力继续存在，不为了延长收集把票篮硬性限为一张。候选插曲必须同时支持一场和多场；逐场候补与金额变化逐项确认。
- `PREF_FLEXIBLE_ATTENDANCE` 会触及“购票尝试不直接修改票篮”的现行契约。若采用，必须先正式修改该边界，明确只有用户确认的候补替换可以形成新篮子快照；不得在源码中例外绕过。
- 票坊后整理只改变装饰层，不增加 PNG、账号绑定、分享任务或二次随机。首选仍是现有合法 SVG 与打印媒介。
- 若 `sessionStorage` 不可用，模组可在当前页面内存中继续；恢复失败仍安全返回票篮。无 JavaScript 继续显示既有静态“暂未开票”降级。
- 国家版本切换继续保留稳定 ID 与数值，并重新解析受理偏好、插曲、复盘和票面辅助层文案。

### CRE-05｜事务插曲库与选择规则

- 状态：候选，首轮只应选取最小子集
- 内容类型：可复用票务事件与互动规则
- 适用时间层：表站“现在”
- 内容目的：让现实购票中的排队、分批放票、来源不明、费用叠加和库存回流形成可学习的选择，而非随机弹窗
- 预期入口：水稻网处理前后、跳楼机报价与保底收束
- 设定边界：事件只消费已有场次、分区、价格、平台和状态；不伪造真实其他用户、真实库存、现实时间或后台连接
- 正式迁入目标：人工采纳后拆入 `BP-MOD-TICKETING` 的处理节拍、分支、状态与本地化内容结构

#### CRE-05 内容正文或叙事蓝本

候选插曲按职责分组，不要求全部进入第一版：

| 候选 ID               | 合格触发                   | 玩家可见信息                                                                  | 主要选择与明示后果                                                                               | 实际所得／变化                                           | 单项时间 |
| --------------------- | -------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | -------------------------------------------------------- | -------- |
| `INC_RELEASE_WINDOW`  | 普通线路不可用             | 原席区暂不可受理；下一批次状态未知；如有真实候补分区则同时列出价格            | 保留原区并再次走普通线路；逐项确认候补并返回提交；返回票篮                                       | 路线标签、可选改区、金额变化、受理簿记录                 | `20–40s` |
| `INC_STATUS_SOURCES`  | 第一次结果前               | 三条状态分别标为“场馆确认／平台延迟／外部未核实”，不显示假在线人数            | 采信场馆确认继续标准路线；查看延迟记录获得复核痕迹后继续；查看外部方案进入清楚标识的跳楼机报价页 | 渠道选择、来源复核痕迹、后续可见信息                     | `20–35s` |
| `INC_NETWORK_RECEIPT` | 叙事网络波动               | 本次请求未获结果、篮子仍保留、重复点击不会提高概率                            | 按原请求重连；保存屏幕内中断记录后返回票篮；正常退出                                             | 既有网络 Ending、重连标签、受理簿中的断线条目            | `15–30s` |
| `INC_PRIORITY_LEDGER` | 查看跳楼机原报价或挽留     | 同时显示 `baseTotal`、`50%` 附加、`48%` 挽留最终附加或 `25%` 失败服务记录语义 | 展开来源与费用审阅后再接受／拒绝；直接作出同等可见的接受／拒绝；返回标准路线                     | 既有路线与 Ending、费用审阅痕迹、组合印章外围构件        | `25–50s` |
| `INC_RETURN_REVIEW`   | 三次上限后的回流收束       | 明确列出原席区及经用户预设的真实候补分区                                      | 接受原席回流；逐项确认候补后普通成功；返回票篮                                                   | `returned-seat` 内部纹理、最终分区与金额、偏好是否保持   | `15–30s` |
| `INC_MANUAL_REVIEW`   | 三次上限后的人工复核收束   | 当前票篮摘要始终固定在同屏；系统给出一项待核对字段                            | 从同屏信息选择正确的场次／分区／金额；错误时直接解释并允许再次选择，不降低成功率；也可返回票篮   | `manual-review` 内部纹理、复核痕迹；提供一次无计时掌握感 | `20–40s` |
| `INC_BASKET_SPLIT`    | 多场次篮子且出现部分不可用 | 逐项列出已确认、待回流与不可用状态                                            | 保留整篮继续；明确释放某项并继续其余场次；返回票篮                                               | 新篮子快照、总价、逐项结果与处理记录                     | `30–60s` |

第一轮推荐只验证四项：`INC_STATUS_SOURCES`、`INC_RELEASE_WINDOW`、增强后的 `INC_PRIORITY_LEDGER` 与 `INC_RETURN_REVIEW`。`INC_BASKET_SPLIT` 会显著改变结果和金额模型，应独立评审；`INC_MANUAL_REVIEW` 需要证明同屏核对确实有趣而不是无意义验证码，未通过体验测试时不加入。

#### 事件编排规则

1. `runSeed + preferenceId + basket performanceIds + attemptCount + phase` 只派生合格事件顺序，不从标题、DOM 顺序或翻译文字猜测；
2. 同一事件一轮最多出现一次，来源审阅和挽留同样不重复；
3. 预检事件不能决定最终概率结果，结果仍在一次提交时只抽取并锁定一次；
4. 网络不连续、三个需重新提交节点上限和普通成功收束继续成立；
5. 玩家选择不能静默加入场次、改区、进入高价路线或增加费用；
6. 事件发生后立即形成一行人类可读处理记录，并在最终票面安全区映射为有限非文字痕迹；
7. 如果事件文案需要新增场馆、灾害路线、视线遮挡、无障碍、职业或组织事实，先进入内容研究与人工审核，不从地点备注自动生成公开结论；
8. 九国家版本按同一事件 ID 提供等价内容；缺失任何运行时消息时整个候选事件不进入该构建，而不是回退炎语。

#### CRE-05 素材与实现提示

- 现实平台资料只支持“等待、分批释放、机器人挤压、来源混淆、费用叠加、推测票源”等抽象问题；事件名称、品牌、排队号、数值与界面必须项目原创。

#### CRE-07 内容正文或叙事蓝本

##### 联动一：场次与票务形成闭环

- 从可售场次详情进入 `/tickets/` 时，可以只预选该 `performanceId`，但不自动勾选或提交；用户仍确认分区与票篮。
- 成功凭单和受理簿中的每个场次可以返回对应场次与剧目详情；链接使用稳定 ID，不从显示标题搜索。
- 多场次结果可以按日期或城市在屏幕受理簿中排序查看，但逐场票仍保持独立，不建立新的巡演事实。

这一层主要提高整站可用性，也让“换一个场次或场馆重新玩”成为自然动机。它不需要污染、解锁或长期进度。

##### 联动二：受理复盘使用“场记／剪辑”语言

《红丝绒》的蓝卡坞片场、拍摄和旧剧团后续语境，可以抽象转译成一次可选的“处理复盘”：同一组稳定事实依次显示“访客看到的动作、平台给出的状态、最终写入凭单的事实”。它不是隐藏真相的第二份结果，而是把已经发生的 `choiceHistory / endingHistory / journeyTags` 换成三列或三段可读视角。

该复盘服务两个隐喻：

1. 旧式剧团试图让现实服从预定剧本；现代票务平台也试图用等待、稀缺和加价把访客写进固定路径；
2. 玩家拒绝、复核、改区或等待回流，是一次被记录的“即兴”，新剧团选择保存批评和过程，而不是抹去不合脚本的部分。

首轮只使用项目原创的“受理记录、场记线、剪辑顺序”语言，不直接写傀影、酒神、Miss.Christine、剧作家或其他角色台词，不复刻官方摄影机玩法、PV 镜头或活动 UI。

##### 联动三：普通的证据解释回路

当本轮场次或剧目在 1084 快照中确有稳定关联记录时，受理簿末尾可以提供一个低干扰普通链接，例如“查阅早期同名剧目登记”。它只导航到合法页面或预填里站搜索；关闭脚本时仍是普通链接。

这一层必须满足：

- 关联由稳定 `productionId`、`performanceId` 或经过人工确认的关系拥有，不根据标题相似猜测；
- 关键关系固定可达，不依赖污染概率；
- 里站不知道用户是否购票，不修改等级 `0` 事实，也不向表站回写污染；
- 返回表站和浏览器历史保持正常；
- 如果普通链接已经足够，不新增关系图、解谜面板、档案钥匙、二维码解锁或进度门槛。

##### 集成战略的抽象用法

《傀影与猩红孤钻》只提供四项抽象启发：一轮有限条件、少量遭遇、过程痕迹、多种结果。本站将其压缩为“一个受理偏好、至多两个插曲、既有七 Ending、一个受理簿与票面”，不采用分队、楼层、战斗、藏品、难度 `0–15`、每日任务或结局解锁条件。

现有 [`archive-anomalous-ticketing.md`](archive-anomalous-ticketing.md) 继续是独立延期创意。未来若启动旧席位异常回应，应有自己的入口、条件、结局、退出、污染关系和蓝图，不作为本草稿的隐藏第四幕。

#### 候选成熟顺序

以下是风险递增的产品顺序，不是已批准一次性开发计划：

1. **先让已有深度可见：** 路线受理簿、印章检视镜；
2. **再增加玩家能控制的差异：** 三项受理偏好、四项最小插曲、票坊后整理；
3. **再验证短时复玩：** 如确有价值，保留同标签页最近三轮；
4. **最后讨论跨模块与长期系统：** 普通档案链接先行，状态桥接、公开编号、部分成功和旧席位异常分别立项。

第一阶段只改变首轮结果分布并让已有深度可见，用来验证“玩家是否因为更常进入、看见并理解自己的路线而愿意重玩”；第二阶段再验证“有后果的偏好和插曲是否比随机 Ending 更能驱动重玩”。如果两者都不成立，不应用长期收藏或更复杂状态机掩盖问题。

### CRE-10｜首轮实验实施计划与样张门禁

- 内容目的：用一个可运行、可丢弃的低风险样张验证现有路线是否值得被看见，以及主动票面整理是否产生足够选择感
- 预期入口：沿用 `/tickets/` 建篮与 `/tickets/partner/` 处理流程，只扩展成功结果阶段
- 设定边界：不新增 Ending、事务插曲、长期收藏、跨板块状态或真实服务；只调整普通线路首轮既有结果分布，不把实验分支实现反向解释为 active 蓝图契约
- 正式迁入目标：人工体验并选择“采纳／修改后再审”后，才把稳定结论迁入 `BP-MOD-TICKETING` 及必要的基础蓝图

#### 本轮假设

1. 把当前已经记录但不易察觉的 `endingHistory`、`journeyTags`、渠道和金额展开成短受理簿，能让玩家复述“这张票是怎样得到的”；
2. 只解释本轮已激活印章构件，不陈列空槽、稀有度或完成率，也能形成观察和比较欲；
3. 成功后由玩家主动选择一种不改票面事实的印制处理，能让纪念票获得个人决定，而不是再增加一层随机掉落；
4. 把首轮普通渠道直达成功率降至 `12%`、并把让出的概率转入“不可用”分支，能让玩家更常看见已有互动，同时不增加网络空转或后续重试长度；
5. 若以上四项仍不能让体验者愿意换一条路线重玩，就不进入受理偏好、插曲库或长期收藏开发。

1. 固定走一次直接成功路线，说明受理簿和印章检视分别告诉了自己什么；

- 合并动作：人工确认后在 `CRE-08` 保留或删除长期方向；若启动，单独建立蓝图草稿和开发计划。
