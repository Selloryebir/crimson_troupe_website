## 正文

### 审计方法与基线结论

本轮由三名只读审计智能体分别承担架构与治理、运行时与边界攻击、UX/UI 与多文字系统压力检查；主智能体逐项回答后，再由原质询者复核。重复问题合并为同一条答辩，不为数量保留同义问题。全部质询均已有明确技术结论或人工答案；这里的“答辩闭合”只表示问题和处置方向明确，不表示整份建议已获人工采纳或源码已经修复。

主智能体使用 Node.js `24.19.0` 复验当前基线：`quality:full`、三语言 `validate:content:preview`、`validate:locales:preview`、`validate:states`、默认 `build` 与 `validate:build` 均通过；默认构建生成 32 个 HTML 页面。上述结果证明当前已编码断言未失败，不证明未编码的契约、浏览器行为或正式批准流程成立。

当前不应推翻的基础包括：参数化但独立的双时间层路由、只列 `Performance` 根实体并派生依赖的根集合、`editionId / routePrefix / locale` 分离、显式语言包注册、搜索和票务消费构建快照、有限命名构建预设、素材权利摘要、蓝图主/相关追踪模型，以及按变更能力调度最小检查的原则。

##### REC-01 最小落地

1. 建立 `rootSetId -> ContentRootSet` 显式注册，由 `resolveContent(context)` 内部解析，不允许默认参数与 context 平行表达同一选择。
2. 将严格策略传入本地化解析与资格检查；可部署预设遇到任何回退、旧译或缺失均在页面生成前失败。
3. 为作者诊断提供显式函数参数或专用检查命令，按记录返回 `sourceLocale`；它不生成网站，也不成为新的构建预设。
4. 提供一个构建范围解析 API，先纳入本地化记录，随后纳入 Artwork 规范化元数据和座席拓扑；不把二进制或全部语言包复制进快照对象。
5. 真实变体存储和批准能力作为独立后续切片，不与两种语言译文制作混写。
6. 将九枚已注册国家徽记定义为可常驻所有构建产物的全局品牌基础资产；不为其增加条件化导入、按 profile 裁剪或集合外资产失败断言。

##### REC-01 可观察验收

- context 指向未知或不匹配根集合时在静态路径生成前失败；三个可部署预设均不能生成含回退记录的页面。
- 集合外 Performance、Production、Location、剧目封面和票务拓扑不进入页面消费者或内容产物闭包。
- 诊断命令能够报告记录级来源，但不能输出第四种可部署站点。
- 在真实变体能力完成前，README、架构说明和交付报告不再把适配壳描述为已经支持并行基线。
- `showcase` 可以包含九枚徽记文件，但只显示当前炎语状态；preview 选择器只显示其构建集合，未构建国家仍不产生页面或入口。

##### REC-01 非目标

- 不引入 CMS、数据库、自由组合环境变量或第二棵全量内容树。
- 不把图片字节、全部翻译包或每个辅助函数塞入同一个巨型快照对象。
- 不为数个小型已注册徽记建立条件化资源管线；该豁免不得延伸到剧目封面、票务素材或其他内容资产。

##### REC-02 最小落地

1. 从当前 snapshot 的稳定记录和真实消息消费组生成源修订；集合外实体或不相关消息不使目标记录失效。
2. 将目标语言作者输入与严格运行时包区分：前者允许 typed partial，后者只能由严格解析的完整结果生成。
3. 在批准为空的当前阶段先设计并验证摘要边界，不编造批准记录；首次批准前完成场次、根集合和站点公共摘要拆分。
4. 座席与 Artwork 的规范化可见参数进入对应闭包；纯构建缓存、文件路径重排等非可见实现细节不应无条件触发人工重审。

##### REC-02 可观察验收

- 修改集合外剧目不会让现有语言整份 `programs` 过期；修改一条当前场次译文只影响该稳定记录及其真实消费者。
- 修改封面焦点、裁切、记忆色、标题明暗、污染参数或座席拓扑会使对应批准资格失效。
- 修改无关页脚标点不会伪装成十二个场次分别需要批准；全局站点单元仍能独立失效。

##### REC-02 非目标

- 不做字段级审批、人员与时间流水账或任意版本历史。
- 不因当前批准集合为空而伪造 formal 数据验证流程。

##### REC-03 可观察验收

- 任一根成员或焦点与所属世界不一致时，构建在静态路径生成前失败。

- 新页面消费者直接导入 raw registries 时 lint 失败，改为消费 snapshot API 后通过。

##### REC-03 非目标

### 质量门禁与安全边界

#### REC-06｜让多语言与浏览器风险进入最小必要门禁

- 状态：候选，答辩已闭合，待人工判断
- 优先级：P0/P1
- 价值：让阶段验收覆盖实际宣称的五语言预览，同时保持日常修改不重复执行全局检查
- 成本：中
- 推荐结论：修正按能力调度的最小检查，并在阶段收口时只追加一次 preview 专属 locale、构建和产物链；建立小型代表性浏览器冒烟矩阵

##### REC-06 原因

##### REC-06 最小落地

1. 日常 `quality -- <paths>` 只追加与路径对应的内容、locale 或状态验证，不把所有代码改动升级为双构建。
2. 阶段收口运行一次完整质量门禁；其后只运行 preview 专属 locale、build、output 和代表性浏览器冒烟，不重复前述子命令。
3. 浏览器矩阵至少包含一个表站和一个里站无 JS 页面、一个搜索初始化失败页面，以及日/俄/希最长头部样本；人工艺术判断仍为独立验收。
4. 远端边界同时约束源码 API 和静态产物常见载入通道。

##### REC-06 可观察验收

- 故意在哥伦比亚、米诺斯或乌萨斯目标文本留下意外汉字，在东国语留下已定义的简体中文残留或错误字形，或制造漏包、错路由、票面溢出时，相应最小或阶段门禁失败。
- 纯文档改动仍不运行 Astro、构建或浏览器；单个常规 TypeScript 改动不无理由执行双 profile 构建。
- 代表性浏览器证据可复现且不形成全站截图审批系统。

##### REC-06 非目标

不建立全语言乘全路由乘全视口的截图矩阵，不引入重量级视觉回归平台，不重复运行同一质量门禁。

### 当前实现中的非问题结论

- 票务状态恢复会按当前候选重新验证票篮、分区、价格和票号，未发现可利用的持久化篡改路径。
