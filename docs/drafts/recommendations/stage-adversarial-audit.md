## 正文

### 审计方法与基线

本轮由主智能体负责答辩，三名只读审查智能体分别负责架构、工程与 UX/UI。每名审查者先独立提出带源码或蓝图定位的高置信质疑；主智能体依据 active 蓝图和当前实现作答，再由原审查者进行第二轮反驳或确认。没有证据、仅为凑数或已经被正式契约反驳的问题不进入待修复结论。

审计沿用上一轮已经实际通过的门禁证据，不为了记录审计再次运行耗时检查：Showcase 构建为 86 页；九语言 Preview 构建为 766 页、10,333 条链接；完整 `verify`、Preview 内容/语言/静态产物和浏览器流程均已通过。当前根集合的 28 个场次、14 个剧目、双时间层归属、前后一年窗口和单时间层同剧目最多三次均未发现数据错误。

已经确认有效的防线包括：语义化主区域与跳过导航、原生语言选择器、无 JavaScript 降级、污染保护区与可靠退出、减少动态效果终态、票务焦点移动、搜索 DOM 安全写入、票面动态文本转义、会话状态恢复校验，以及无遥测、Cookie、长期本地存储、个人信息收集或运行时第三方请求。

#### REC-01｜让内容校验只针对并完整覆盖最终构建对象

- 状态：已通过人工审核，等待正式迁移与实施
- 优先级：P1
- 价值：防止验证器检查 Baseline 或隐藏全局数据，而最终页面实际消费另一份 Preview 变体或非法闭包
- 成本：中
- 推荐结论：后续以一个最终选中变体和一个构建闭包统一驱动解析、校验、批准摘要、本地化新鲜度与运行时消费者

##### REC-01 原因

- `ARC-01`：1084 里站只允许 `folio` 的 active 契约目前只在外围验证脚本中执行；`validateContentRootSet()` 和 `resolveContent()` 的内容解析边界可接受引用原创剧目的里站根集合。主答辩确认这是运行时内容不变量，不应只依赖 `verify`；架构复核同意关闭争议。
- `ARC-02`：等级 3 页面写死 `the-carnival`，但投影 schema 和根闭包没有声明该依赖。当前数据恰好包含该剧目，不代表依赖成立。主答辩明确它只是当前临时投影身份，不是永久产品事实；架构复核同意用显式投影身份或独立投影资产建模。
- `ARC-04 / ENG-01`：`assertContentBundle()` 未把当前快照传给 `assertLocalizationSourceFresh()`，集合外地点变化可以错误阻塞当前构建；运行时诊断反而已经正确按快照收敛。两名审查者均确认必须修复。
- `ENG-02`：实际解析会选择 Preview 变体，但完整校验和批准摘要仍取 Baseline。当前特殊 Preview 恰好引用相同对象，只是掩盖了缺口；答辩确认最终选中变体必须同时进入解析、依赖闭包、校验和摘要。
- `ARC-S1`：`validateContentRootSet(..., context?)` 通过可选参数静默决定是否执行时间窗口业务规则，同名函数可以返回“部分验证成功”。架构复核确认应让完整运行时校验强制接收 `BuildContext`；结构测试若有需要，拆成名称明确的内部函数。
- `ARC-S2 / ENG-08`：`assertContentBundle()` 接受注入数据，却调用读取全局矩阵的 `assertPerformanceOfferMatrix()`；最终 `TicketOffer[]` 本身也未在统一闭包内完整验证。注入重复分区和负价格时可假通过，属于真实验证缺陷。

##### REC-01 最小落地

1. 先解析最终变体，再从该结果建立场次、剧目、地点、Artwork、座席、投影和本地化闭包。
2. 完整根集合校验强制接收构建上下文与剧目注册表；里站逐项验证 `sourceKind = folio`。
3. 让批准摘要和译文新鲜度只消费最终闭包；全库健康诊断不得阻断当前获选集合构建。
4. 对最终 `TicketOffer[]` 直接执行分区、价格和座席拓扑约束；报价矩阵校验不得读取未注入的隐藏全局。

##### REC-01 可观察验收

- 注入里站原创剧目、范围外旧译、Preview 变体不同依赖、重复或负数 offers 时，各自只在正确边界失败；范围外候选不阻断当前构建。
- 更换等级 3 投影身份后，依赖闭包自动跟随，页面不再依靠某个普通剧目恰好入选。

##### REC-01 非目标

不在本轮决定等级 3 最终剧目和请柬文案，不建立第二套全库内容系统，也不把作者全库诊断混回发布门禁。

#### REC-02｜让作者层容纳集合外候选，解析层保持严格完整

- 状态：已通过人工审核，等待正式迁移与实施
- 优先级：P1
- 价值：避免每个尚未获选的候选地点、场次或剧目都迫使九语言同步补齐，同时保证入选内容绝不缺译
- 成本：中
- 推荐结论：作者源采用局部记录，只有构建快照中的 `ResolvedLocalization` 对获选闭包要求完整

##### REC-02 原因

- `ARC-03`：`AuthoringProgramContent` 虽允许局部记录，实际九语言文件却使用完整 `Record`，新增集合外候选仍会触发全语言修改；这抵消了根集合隔离候选与公开内容的作用。
- `ARC-05`：`PerformanceContent.searchDetail` 没有运行时消费者，搜索摘要由其他字段重新拼装；该字段却增加九语维护、修订指纹和批准失效成本。
- `ARC-06`：语言无关 `effectiveDateTime` 与九份手写 `dateTimeDisplay` 平行编码日期事实，现有校验只能保证字符串存在，不能保证显示日期与结构事实一致。

##### REC-02 主答辩与复核结论

| 质询 ID  | 主答辩                                                                 | 第二轮复核                                       |
| -------- | ---------------------------------------------------------------------- | ------------------------------------------------ |
| `ARC-03` | 允许集合外候选先入领域库；获选后由解析快照强制九语完整                 | 回答成立，无需产品裁决                           |
| `ARC-05` | 当前蓝图未要求自定义搜索摘要；没有近期消费者时删除 `searchDetail`      | 回答成立；未来若需要定制摘要应重新定义唯一消费者 |
| `ARC-06` | 结构化时间是唯一事实；各语和里站可有格式策略，但不能自由改写年月日时分 | 回答成立；具体文风不是技术修复前置条件           |

##### REC-02 最小落地

- 作者侧地点、场次与剧目本地化改用 `Partial<Record<...>>` 或现有 `AuthoringProgramContent`；解析结果保持完整只读类型。
- 删除无消费者的 `searchDetail` 及其修订/摘要参与关系，搜索继续从唯一可见事实生成摘要。
- 用结构化日期和有限格式策略生成显示值；若暂时保留手写文学日期，至少校验结构年月日时分等价。

##### REC-02 可观察验收

- 集合外新增候选不要求同步九语言；将其加入根集合后，缺少任一当前构建语言记录会在生成路径前失败。
- 日期显示无法与 `effectiveDateTime` 产生不同日期或时间。

##### REC-02 非目标

不降低入选内容的九语言完整度，不批准任何新候选内容，也不在本阶段决定各语言最终日期文风。

#### REC-03｜补齐快照不可变性、票面边界与构建期资源效率

- 状态：已通过人工审核，等待正式迁移与实施
- 优先级：P1（不可变快照、票面溢出）；P2（缓存与隐藏资源加载）
- 价值：使 active 契约中的“不可变快照”真实成立，避免长标题票面重叠，并减少随页面数量放大的重复计算与无效下载
- 成本：小至中
- 推荐结论：先修复确定性错误，再做不改变公共契约的局部缓存和加载优化

##### REC-03 原因

- `ENG-04`：票面标题在缩到最小字号后仍可能超过 `maxLines`，渲染器会继续输出全部行并与后续字段重叠。
- `ENG-05`：当前只冻结快照和部分记录外层；本地化包内部、Artwork 污染对象和座席数组仍可变，与 active 蓝图的“不可变快照”不一致。
- `ENG-06`：页面和布局会对同一快照、同一语言重复解析本地化并计算修订指纹。当前 766 页规模尚无异常，但成本随内容与语言增长重复放大。
- `ENG-07`：Hero 或详情中的等级 3 投影图在等级 0 也被标为 eager，正常访客会提前下载不可见大图。

##### REC-03 主答辩与复核结论

| 质询 ID  | 主答辩                                                                     | 第二轮复核                 |
| -------- | -------------------------------------------------------------------------- | -------------------------- |
| `ENG-04` | 最小字号后执行安全省略或失败回退，并加入多语长标题测试                     | 回答成立，属于实现缺陷     |
| `ENG-05` | 不把不可变性降格为团队约定；深冻结选中闭包或建立真正不可变副本             | 回答成立，属于 active 契约 |
| `ENG-06` | 按 snapshot + edition 缓存，或把页面解析结果传给布局；当前只列低优先级优化 | 回答成立，禁止借机大改 API |
| `ENG-07` | 隐藏投影资产使用 lazy 或等级 3 再赋值                                      | 回答成立                   |

##### REC-03 最小落地

修复票面布局与深层不可变性并增加聚焦测试；随后只选择一种最小的本地化复用方式。投影资源加载修正不得让无 JavaScript 或等级切换留下空图、布局抖动或远端请求。

##### REC-03 可观察验收

- 极长的多语言标题不会覆盖票面后续字段；快照闭包内对象在开发测试中无法被后续消费者修改。
- 同一页面不重复执行同一快照、语言的完整诊断；等级 0 初始资源不再 eager 下载不可见等级 3 大图。

##### REC-03 非目标

不引入客户端框架、运行时服务或全站图片管理库，不以当前可接受的 17 MB 构建体积为由提前重写内容架构。

#### REC-04｜让无障碍与响应式门禁证明真实交互结果

- 状态：已通过人工审核，等待正式迁移与实施
- 优先级：P1
- 价值：防止 CSS 裁切掩盖真实交互控件越界，并让污染变化与请柬流程对键盘和辅助技术可验证
- 成本：小
- 推荐结论：补少量代表性断言，不扩展为全语言、全路由、全视口的截图笛卡尔积

##### REC-04 原因

- `UX-01`：搜索等页内事件提高污染值时，控制器只改数据属性；现有 live region 仅在随后打开请柬时更新，缺少 active 门禁要求的短本地化状态变化公告。
- `UX-02 / ENG-09`：正式蓝图列出 `320 / 390 / 768 / 1280`，浏览器门禁没有 768；620 和 960 的关键 CSS 断点也使 768 不能由两端视口代替。人工已确认当前自动化支持证据限定为 Chromium，不从现有结果推断 Firefox 或 WebKit 兼容。
- `UX-03`：页面使用 `overflow-x: hidden/clip`，现有横向丢失检查收集越界元素却没有断言关键交互元素或当前焦点的真实边界，可能以裁切制造假通过。
- `UX-04`：请柬使用原生 dialog、关闭后恢复焦点并保留合法目标，代码防线较好；但当前浏览器门禁只证明鼠标路径，没有完整证明键盘触发、焦点进入、Escape、焦点返回和继续链接。

##### REC-04 主答辩与复核结论

| 质询 ID           | 主答辩                                                                                  | 第二轮复核                                             |
| ----------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| `UX-01`           | 控制器提供独立本地化 live region，只在交互导致等级变化时发布短公告；不朗读整份请柬      | 回答成立                                               |
| `UX-02`、`ENG-09` | 增加覆盖代表页面族的 768 场景；九语言、四视口和关键页面族采用组合覆盖，不做完整笛卡尔积 | 回答成立；人工确认当前只以 Chromium 作为自动化支持证据 |
| `UX-03`           | 对受保护导航/退出、可交互叙事控件和当前焦点的 bounding box 断言；排除纯装饰节点         | 回答成立                                               |
| `UX-04`           | 新增一条代表性完整键盘请柬路径，不复制同类测试                                          | 回答成立                                               |

##### REC-04 最小落地

只扩展现有 Chromium 浏览器门禁：增加一个 768 组合样本、一条键盘请柬流程、一次污染等级变化公告断言，以及 320 等风险视口下关键可交互元素和焦点边界检查。交付结论明确写作“通过 Chromium 验证”，不声称已经自动验证 Firefox 或 WebKit。

##### REC-04 可观察验收

- 交互导致等级改变时辅助技术收到一条简短本地化公告；初次加载不主动朗读请柬。
- 768 布局和 320 等污染高风险布局无内容丢失；隐藏 overflow 不能让越界控件通过。
- 键盘打开、Escape、关闭后焦点返回和继续合法链接均由同一测试证明。

##### REC-04 非目标

不建立全量截图系统，不把纯装饰的可控越界判为功能失败，也不在当前阶段增加 Firefox 或 WebKit 自动化门禁。

- 状态：已通过人工审核，等待正式迁移与实施
- 优先级：P2

- 价值：区分当前真实缺陷与未来规模风险，避免以审计名义过早重写
- 成本：无
- 推荐结论：当前规模不进行框架级性能改造；新增语言或内容批次后再以构建时间、产物体积和广义搜索结果数量作为触发证据

##### REC-07 原因

当前 Preview 为 766 个 HTML、约 17 MB、最大单页约 56 KB，构建与浏览器验证已经通过；页面数量由快照推导而非硬编码。UX 复核也确认东国语环境的希腊／俄文字距防线、三类座席图与原生选择器、污染保护页脚及 320px 乌萨斯语退出路径均无新的高置信回归。

##### REC-07 最小落地

本轮不改。后续内容或语言扩展时复用现有门禁观察构建时间、产物和搜索结果长度；只有出现可重复退化再提出针对性优化。

##### REC-07 可观察验收

未来优化提案必须带可复现的规模或体验证据，不能仅凭页面数量增长推定需要换框架、CMS、数据库、分页或模糊搜索库。

##### REC-07 非目标

不把当前已通过的安全、布局与性能路径重复列为开发任务。

#### REC-08｜采用显式首页策展与最低限度搜索组织

- 状态：已通过人工审核，等待正式迁移与实施
- 优先级：P1
- 价值：避免首页随场次库无限增长，并在不引入复杂搜索系统的前提下提高结果可扫读性
- 成本：小至中
- 推荐结论：首页使用显式、内容驱动的精选场次集合；搜索采用标题优先和页面类型分组

##### REC-08 原因

- 首页当前展示完整本季集合，内容扩展后会逐步复制完整列表页、削弱“查看全部”的意义并增加窄屏滚动成本。人工确认采用显式策展规则，不让组件通过 `.slice()` 暗中决定访客看到什么。
- 当前 substring 搜索结果按索引顺序全量平铺。人工确认只增加标题优先与页面类型分组，以较低成本改善广义关键词结果；当前没有证据支持模糊搜索库、分页或复杂相关性权重。

##### REC-08 最小落地

- 在语言无关内容根中以 `homepagePerformanceIds` 声明表站与里站各自的首页精选 `performanceId` 有序集合；成员必须属于对应时间层当前本季集合。它与现有单个 Hero 焦点 `featuredPerformanceId` 职责分离，首页节目区只消费前者，完整列表页继续消费全部本季集合。
- 搜索保持现有索引、时间层与语言隔离；在客户端对命中项执行稳定的标题命中优先排序，再按页面、场次、剧目等现有结果类型分组显示。相同优先级内保持索引原顺序，避免不透明评分。

##### REC-08 可观察验收

- 增加未入选的本季场次不会自动拉长首页；改变显式精选顺序会确定性改变首页顺序，“查看全部”仍到达完整集合。
- 标题命中排在仅摘要或关键词命中之前；结果按已有类型获得可理解分组，零结果、键盘路径和语言／时间层隔离保持不变。

##### REC-08 非目标

不建立个性化推荐、随机策展、分页、模糊匹配、复杂评分或搜索服务；不把首页精选集合误作完整本季集合。
