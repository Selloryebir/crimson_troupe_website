# BP-MOD-TERRA-TIME｜网站泰拉时间

## 用户结果

表站与里站始终使用各自明确的网站泰拉时间判断本季和历史场次；当前静态预览保持稳定，未来启用表站时间流动时不需要让页面、搜索或票务各自实现日期算法。

## 边界

- 拥有每个时间层的网站时钟策略、当前泰拉时间解析接口，以及固定与未来锚定时钟的替换边界；
- `Performance` 的排期和运营状态由 `BP-FND-DOMAIN` 负责，页面集合和票务资格只消费本模组解析的 `siteTerraNow`；
- 不拥有现实部署调度、浏览器时区、场次文案、运营状态、污染状态或泰拉历之外的世界观时间推演；
- 当前阶段不启用时间流动，不决定未来现实锚点、泰拉锚点、流速、日历进位算法或重建频率。

## 时钟接口与策略

- 所有消费者通过一个网站时钟接口按 `world` 与构建上下文取得 `siteTerraNow`，不得直接读取浏览器日期、构建日期或各自保存时间常量；
- 接口允许接收明确的现实时间输入，以便测试和未来锚定提供者使用；当前固定提供者忽略该输入并返回配置值；
- 时钟策略至少区分 `fixed` 与未来可注册的 `anchored`。策略选择属于有限构建配置，不由 URL、locale、用户设备或页面组件决定；
- 当前表站和里站都使用 `fixed`：表站为泰拉历 `1098-09-01 00:00`，里站为泰拉历 `1091-07-01 00:00`。这些值用于预览分类，不要求直接显示；
- 里站是 1091 历史快照，始终拒绝流动时钟。污染只改变会话中的可见投影，不能改变里站时钟；
- 未来表站可以在另行获准的阶段使用 `anchored`：以一个明确现实时间点、一个泰拉时间点和明确换算规则解析构建时的 `siteTerraNow`；
- 静态站点启用流动后，集合在构建快照中重新计算并通过计划性构建发布。浏览器端不得各自重算或在同一静态产物中产生不同集合；若未来需要客户端实时跨日，必须另行修改正式契约。

## 分类协作

- `effectiveDateTime >= siteTerraNow` 属于本季或未来集合，`effectiveDateTime < siteTerraNow` 属于历史集合；
- 运营状态不改变分类：未来取消场次仍在未来集合，过去未完成或取消场次仍在历史集合；
- 构建快照只计算一次分类，列表、首页、详情、搜索、票务和验证器读取同一结果；
- 改期后使用新的 `effectiveDateTime`，但不改变稳定场次身份。

## Demo 基线

- 当前源码通过单一网站时钟接口与 `effectiveDateTime` 派生集合，保持表站三个未来场次、里站四个历史与五个未来场次；
- 当前两个时间层均使用固定提供者，不随现实时间、浏览器时区或刷新变化。

## Formal 增量

- 建立单一网站时钟接口和两个固定提供者，按上述临时时间从构建快照派生集合并移除长期手写分类；
- 保留未来表站锚定提供者的接口位置，但不实现锚点、换算、构建调度或客户端实时流动；
- 为固定时间、边界相等、改期、取消状态和里站拒绝流动增加确定性检查。

## 验收

- 给定相同时钟输入和场次排期，所有消费者得到相同集合；
- 当前构建保持既有可见分类，不因现实日期、浏览器时区、刷新或国家版本变化而漂移；
- 里站无法通过构建预设或客户端状态启用时间流动；
- 未来替换表站时钟提供者时，页面、搜索、票务和内容记录不需要新增各自的日期算法；
- 未配置或未知时钟策略在生成页面前明确失败，不静默回退到浏览器时间。
